# บทที่ 6 การทดสอบและการประเมินผล

ตัวเลขทุกตัวในบทนี้สืบย้อนได้ถึงไฟล์ใน `eval-results/` (ผลลัพธ์ดิบพร้อมคำสั่งทำซ้ำ) หรือถึงสไลด์นำเสนอของคณะผู้จัดทำ (`Cura AI.pdf`) ตามที่ระบุ ณ จุดที่ใช้ ไม่มีตัวเลขใดที่ประมาณการหรือสร้างขึ้นเพื่อรายงานนี้

ชุดทดสอบของ `medcode-api` รันสองครั้ง ครั้งแรกโดยไม่ได้เริ่ม `imed-mock-api` (12 รายการเกิดข้อผิดพลาด "iMed API not reachable" เพราะบริการที่ต้องพึ่งพายังไม่ทำงาน มิใช่ข้อบกพร่อง) ครั้งที่สองขณะที่บริการทำงานอยู่ (ผ่าน 11 จาก 12 รายการ) ความล้มเหลวที่เหลือ คือ `CasesApiIntegrationTest.approveThenReopenRoundTripsAndInvalidatesCache` เป็นช่องว่างด้านการแยกการทดสอบ (test isolation) การทดสอบนี้เรียก `imed-mock-api` ที่ทำงานจริง ซึ่งเขียนลงฐานข้อมูล `imed` บน Postgres จริงและไม่ถูก roll back โดย transaction ของ Spring การรันซ้ำกับระบบจำลองที่ทำงานต่อเนื่องจึงมีแถวสะสมที่การทดสอบไม่ได้คาดไว้ รายละเอียดอยู่ใน `eval-results/SUMMARY.md`

## 6.3 ความแม่นยำของรหัสที่ AI แนะนำ (การประเมินการค้นคืน)

ข้อมูลอ้างอิง (ground truth): สถานการณ์ทางคลินิก 42 สถานการณ์จาก `imed-mock-api/scripts/generate_demo_data.py` แต่ละสถานการณ์กำหนดรหัส ICD-10 (บางสถานการณ์มี ICD-9) ไว้ในโค้ดคู่กับข้อความบันทึกภาษาไทย ข้อความของแต่ละสถานการณ์ถูกส่งไปยัง `POST /suggest` ของ RAG (เฉพาะการค้นคืน ไม่เรียก LLM) แล้วบันทึกว่ารหัสที่ถูกต้องปรากฏหรือไม่และอยู่อันดับใด

| ตัวชี้วัด | ผลลัพธ์ |
|---|---|
| ความแม่นยำอันดับแรก (top-1) ของ ICD-10 | 0/42 (0.0%) |
| ICD-10 ภายใน 8 อันดับแรก (top-8) | 3/42 (7.1%) |
| ICD-9 อันดับแรก (จาก 23 สถานการณ์ที่เกี่ยวข้อง) | 0/23 (0.0%) |
| ICD-9 ภายใน 8 อันดับแรก | 1/23 (4.3%) |

**สาเหตุ:** การตรวจสอบด้วยตนเองยืนยันว่าการค้นคืนโดยทั่วไป *ไม่ได้* ผิดพลาด การสอบถาม `POST /retrieve` ด้วย `"J00 common cold"` ได้ chunk ที่ถูกต้องพอดี โดยมี `score: 1.0` (`via: "exact match: J00"`) แต่ *คำบรรยายอาการจริง* ของเคสเดียวกัน ("ไข้ต่ำ ๆ น้ำมูกใส จาม เจ็บคอ ไอแห้ง เป็นมา 3 วัน") กลับได้รหัสที่ไม่เกี่ยวข้อง ซึ่งมาจากส่วนดัชนีของ PDF อ้างอิงฉบับหนึ่งที่ดูเหมือนแบ่งชิ้นข้อความผิดพลาด **ช่องว่างนี้เกิดเฉพาะกับการค้นคืนแบบคำบรรยายอาการ → รหัสการวินิจฉัย ซึ่งเป็นกรณีใช้งานจริงของผู้ให้รหัส** และเป็นข้อค้นพบที่นำไปปฏิบัติต่อได้มากที่สุด รายงานฉบับเต็ม: `eval-results/rag-accuracy-SUMMARY.md` ข้อมูลดิบรายเคส: `eval-results/rag-accuracy-raw.json`

ข้อสงวน: gold set นี้เป็นข้อมูลสมมุติจากแม่แบบที่คณะผู้จัดทำเขียนเอง (ผู้สร้างคลังเอกสารค้นคืนด้วย จึงอาจมีคำศัพท์ทับซ้อนกัน) การประเมินทดสอบ `/suggest` มิใช่เส้นทาง LLM แบบเต็มผ่าน `/chat` ที่ผู้ให้รหัสเห็นในแอป และใช้แทนการให้คะแนนเทียบกับข้อมูลการให้รหัสในอดีตของโรงพยาบาลจริงไม่ได้

## 6.4 สิ่งที่ไม่ได้ทดสอบ

- การเปรียบเทียบเวลาการให้รหัสด้วยมือกับแบบมี AI ช่วย และการเทียบกับข้อมูลที่โรงพยาบาลเคยให้รหัสไว้ — **อยู่นอกขอบเขตของผลงานครั้งนี้** เพราะไม่มีข้อมูลเวลาหรือปริมาณงานจากโรงพยาบาลทันเวลา และการอนุมานจากการจับเวลาภายในเพียง 1–5 เคส (`Cura AI.pdf`) น่าจะทำให้เข้าใจผิดมากกว่า จึงตัดออก ดูระเบียบวิธีของ Klang et al. ในบทที่ 2
- การแย่งชิงการเขียนเมื่อผู้ให้รหัสหลายคนอนุมัติ/แก้ไขพร้อมกัน
- ความหน่วงของการแนะนำรหัสด้วย RAG ภายใต้ภาระงาน
- ข้อเสนอแนะอย่างเป็นระบบจากผู้ให้รหัส — **อยู่นอกขอบเขตของผลงานครั้งนี้** เพราะไม่มีผู้ให้รหัสจริงพร้อมทดลองใช้ก่อนกำหนดส่ง
- การทดสอบความสามารถในการใช้งาน UI กับผู้ใช้นอกคณะผู้จัดทำ (มีภาพหน้าจอในภาคผนวก ง แต่ยังไม่ได้สังเกตผู้ใช้ภายนอก)
- **ไม่ได้ให้คะแนน `/chat` (เส้นทาง LLM แบบเต็มในเมนู AI ผู้ช่วย) แยกต่างหาก** ประเมินเฉพาะ `/suggest` (หัวข้อ 6.3) เพราะดาวน์โหลดโมเดล `Llama-3.1-EIRAI-8B` ผ่าน Ollama ไม่ได้ในรอบการประเมิน (ไคลเอนต์ Ollama ปฏิเสธการ redirect ข้ามโฮสต์จาก CDN ของ Hugging Face ทุกครั้ง) และ `/chat` ใช้ชั้นการค้นคืนเดียวกับที่ทดสอบแล้ว การแก้ปัญหานี้ภายใต้กำหนดส่งจึงไม่คุ้มกับข้อมูลใหม่ที่น่าจะได้
