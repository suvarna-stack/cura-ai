# บทที่ 2 งานที่เกี่ยวข้องและเทคโนโลยีที่เลือกนำมาใช้

แหล่งอ้างอิงทุกแหล่งในบทนี้สืบค้นและตรวจสอบเมื่อวันที่ 18 กันยายน 2026 คำอธิบายผลิตภัณฑ์ในหัวข้อ 2.1 มาจากเอกสารผลิตภัณฑ์ซึ่งเป็นสื่อทางการตลาด

## 2.1 การให้รหัสโดยใช้คอมพิวเตอร์ช่วย (CAC): แนวทางที่ใช้กันอยู่เดิม

โรงพยาบาลขนาดใหญ่ โดยเฉพาะในสหรัฐอเมริกา ใช้ซอฟต์แวร์ **การให้รหัสโดยใช้คอมพิวเตอร์ช่วย (computer-assisted coding: CAC)** อยู่แล้ว ซอฟต์แวร์นี้อาศัยกฎและการประมวลผลภาษาธรรมชาติ (NLP) อ่านเวชระเบียนและแนะนำรหัสให้ผู้ให้รหัสยอมรับหรือปฏิเสธ ตัวอย่างเชิงพาณิชย์ ได้แก่

- **Solventum (เดิมคือ 3M) 360 Encompass** — แพลตฟอร์มที่รวม CAC การปรับปรุงคุณภาพการบันทึกเวชระเบียนทางคลินิก (clinical documentation improvement: CDI) และการให้รหัส/การตรวจสอบไว้ด้วยกัน โดยผสาน "3M CRS" เข้ากับขั้นตอนการให้รหัสและความถูกต้องของรายได้ (revenue integrity) และแนะนำรหัสจากเอกสารของผู้ป่วยโดยอัตโนมัติให้ผู้ให้รหัสตรวจทาน (3M / Solventum, n.d.)
- **3M M\*Modal CDI Engage** — เครื่องมือ CDI บนคลาวด์ที่ขับเคลื่อนด้วย AI ช่วยให้แพทย์บันทึกเอกสารอย่างมีโครงสร้างขณะเขียน จึงลดความกำกวมที่ผู้ให้รหัสต้องแก้ไขภายหลัง (Healthcare IT News, n.d.)

ผลิตภัณฑ์เหล่านี้สร้างขึ้นโดยยึด **ระบบรหัสของสหรัฐอเมริกา (ICD-10-CM, CPT)** **การติดตั้งบนคลาวด์หรือภายในองค์กร (on-prem) ขนาดใหญ่** และ **สิทธิ์การใช้งานเชิงพาณิชย์แบบคิดตามจำนวนผู้ใช้ / ตามจำนวนสถานพยาบาล** เอกสารสาธารณะที่พบไม่กล่าวถึง ICD-10-TM บันทึกทางคลินิกภาษาไทย หรือคำศัพท์ระบบหลักประกันสุขภาพของไทย (UCS/CSMBS/SSS ใน `medical-glossary.md`) ผลิตภัณฑ์เหล่านี้ใกล้เคียงที่สุดกับแนวคิด "AI ช่วยให้รหัสพร้อมการอนุมัติโดยมนุษย์" ของโครงการนี้ (บทที่ 1 หัวข้อ 1.4) แต่ใช้กับโรงพยาบาลไทยทันทีไม่ได้ เนื่องจากคำศัพท์ การใช้ภาษาปะปนกัน และข้อจำกัดด้านการติดตั้งและถิ่นที่อยู่ของข้อมูล (data residency) (หัวข้อ 2.3)

## 2.2 RAG สำหรับการให้รหัส ICD แบบอัตโนมัติ / แบบช่วยเหลือ: งานวิจัยทางวิชาการในช่วงล่าสุด

การสร้างข้อความเสริมด้วยการค้นคืน (retrieval-augmented generation: RAG) คือการค้นคืนข้อความอ้างอิงที่เกี่ยวข้องก่อนให้โมเดลภาษาตอบ งานวิจัยล่าสุดที่ประยุกต์ RAG กับการให้รหัส ICD และเกี่ยวข้องกับสถาปัตยกรรมของโครงการนี้ (บทที่ 4) มีดังนี้

- **Deppe et al. (2025)** สร้างและประเมินไปป์ไลน์กึ่งอัตโนมัติที่กำหนดรหัส ICD-10 จากข้อความทางคลินิกภาษาเยอรมันที่ไม่มีโครงสร้าง โดยผสานการค้นคืนจากคลังเอกสารอ้างอิงเข้ากับการให้เหตุผลเชิงสร้างข้อความ เป็นระบบที่ตีพิมพ์แล้วซึ่งใกล้เคียงกับบริการ RAG ของโครงการนี้มากที่สุด (ค้นคืนข้อความอ้างอิง → LLM ตอบจากบริบทที่ค้นคืนมาเท่านั้น)
- **Klang et al. (2024)** เปรียบเทียบการให้รหัสด้วย LLM ที่เสริมด้วย RAG กับรหัส ICD-10-CM ที่ผู้ให้บริการทางการแพทย์กำหนด บนเวชระเบียนจริงของแผนกฉุกเฉิน ผู้ตรวจทานที่เป็นมนุษย์เลือกรหัสจาก AI มากกว่ารหัสของผู้ให้บริการในกรณีส่วนใหญ่ (447 ต่อ 277, p < 0.001) นับเป็นหลักฐานที่หนักแน่นที่สุดที่พบว่าการให้รหัสโดยมี RAG ช่วยเทียบเท่าหรือดีกว่ามนุษย์บนข้อมูลจริง และเป็นการเปรียบเทียบกับการให้รหัสในอดีตแบบเดียวกับที่โครงการนี้ยังขาดอยู่ก่อนการนำไปใช้งานจริง (บทที่ 8)
- **งานสำรวจ RAG ในชีวเวชศาสตร์** (*Retrieval-augmented generation in biomedicine*, 2025) ระบุว่าคุณค่าหลักของ RAG ทางคลินิกคือการยึดโยงข้อความที่สร้างกับข้อความต้นฉบับที่ค้นคืนมาและตรวจสอบได้ แทนการพึ่งความจำเชิงพารามิเตอร์ (parametric memory) ของโมเดล บริการ RAG ของโครงการนี้ใช้หลักนี้โดยตรง: พรอมต์ระบบใน `RAG/app/core/rag.py` สั่งให้โมเดล "Answer ONLY using the provided context... If the context does not contain the answer, say you don't know," และการตรวจสอบการยึดโยง (`_verify_codes`) ทำเครื่องหมายรหัสที่คำตอบกล่าวถึงแต่ไม่อยู่ในชิ้นข้อความ (chunk) ที่ค้นคืนมาเป็น `unverified_codes` ก่อนถึงผู้ให้รหัส
- **การเปรียบเทียบ RAG สำหรับการวินิจฉัยเนื้องอกภาษาเยอรมัน** (*To RAG, or not to RAG?*, 2026) ประเมิน LLM แบบเปิดเผยน้ำหนัก (open-weight) ที่ใช้พรอมต์แบบ RAG (Llama 3.1 8B, Llama 3.3 70B) เทียบกับ LLM พื้นฐานสำหรับการให้รหัส ICD-10 / ICD-O-3 พบว่า RAG ช่วยเพิ่มประสิทธิภาพของโมเดลพื้นฐานได้อย่างมาก จึงสนับสนุนการเลือกใช้โมเดลภายในเครื่องขนาดเล็ก (Llama-3.1 8B ผ่าน Ollama โดยมีโมเดล 0.5B ภายในโปรเซสเดียวกันเป็นตัวสำรอง ดูบทที่ 4) *ร่วมกับ* การค้นคืน แทนการใช้โมเดลที่ใหญ่กว่าเพียงอย่างเดียว
- **RuCCoD** (*RuCCoD*, 2025) ผสานการค้นคืนจากฐานข้อมูลรหัสที่มีโครงสร้างเข้ากับการจัดอันดับใหม่ (reranking) ด้วย LLM สำหรับภาษารัสเซีย แสดงว่ารูปแบบ RAG ขยายไปสู่ภาษาและรหัสฉบับดัดแปลงระดับชาติอื่นได้ แบบเดียวกับที่โครงการนี้ทำสำหรับภาษาไทย/ICD-10-TM

ทั้ง 5 แหล่งสอดคล้องกันว่า **RAG ให้ผลดีกว่า LLM ที่ใช้ลำพังในการให้รหัส ICD และการให้รหัสโดยมี RAG ช่วยสามารถเข้าใกล้หรือสูงกว่าผู้ให้รหัสที่เป็นมนุษย์ได้ในบางกลุ่มตัวอย่าง** แต่ทุกการศึกษาใช้ภาษา รหัสฉบับดัดแปลง และข้อมูลของระบบสุขภาพ *เฉพาะแห่ง* และไม่มีงานใดใช้ข้อมูลภาษาไทยหรือ ICD-10-TM ดัชนี RAG ของโครงการนี้ (ICD-10, ICD-9 และเอกสาร PDF อ้างอิง ICD-10-TM สำหรับ PCU — `RAG/data/documents.json`) สร้างขึ้นเพื่อเริ่มปิดช่องว่างนี้ ผลวัดความแม่นยำครั้งแรกซึ่งวัดบนข้อมูลสมมุติเท่านั้นอยู่ในบทที่ 6 (หัวข้อ 6.3) และยังไม่มีการวัดเทียบกับการให้รหัสจริงของโรงพยาบาล

## 2.3 เหตุใดจึงใช้ชุดเทคโนโลยี RAG ภายในเครื่องแทน API ของ LLM บนคลาวด์

คณะผู้จัดทำเลือกไปป์ไลน์ที่ทำงาน **ภายในเครื่องทั้งหมด** ได้แก่ เวกเตอร์ฝังตัว (embedding) จาก `BAAI/bge-m3` ฐานข้อมูลเวกเตอร์ Chroma ที่จัดเก็บถาวรบนดิสก์ และ LLM ขนาดเล็ก (Llama-3.1 8B ผ่านเซิร์ฟเวอร์ Ollama ที่ทำงานบนเครื่องแม่ข่ายโดยตรง (host-native) หรือ `Qwen/Qwen2.5-0.5B-Instruct` ภายในโปรเซสเดียวกันเป็นตัวสำรอง) แทน API ของ LLM บนคลาวด์ (OpenAI, Anthropic, Google เป็นต้น) ด้วยเหตุผล 3 ประการ

**1. ถิ่นที่อยู่ของข้อมูลและกฎหมายไทย** ข้อความในเวชระเบียน (อาการสำคัญ ประวัติการเจ็บป่วยปัจจุบัน ผลตรวจทางห้องปฏิบัติการ) เป็น "ข้อมูลส่วนบุคคลที่มีความอ่อนไหว" ซึ่ง พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA) ควบคุมเข้มงวดที่สุด (บทที่ 5) รายการตรวจสอบก่อนนำไปใช้งานจริงของคณะผู้จัดทำพบว่า PDPC กำลังร่างแนวปฏิบัติเฉพาะด้านสุขภาพ (HLC, 2026) และการส่งข้อมูลไปยังเซิร์ฟเวอร์นอกประเทศมีข้อจำกัดทางกฎหมาย ส่วนภูมิภาค (region) กรุงเทพฯ ที่ Google Cloud เปิดในเดือนมกราคม 2026 (Google Cloud, 2026) **ไม่มี GPU** การเรียก LLM บนคลาวด์ที่ใช้ GPU จึงต้องออกนอกประเทศไทยโดยปริยาย (`medcode-api/docs/DEPLOYMENT-PREP.md` หัวข้อ 3) โมเดลภายในเครื่องเลี่ยงประเด็นนี้ได้ทั้งหมด เพราะไม่มีข้อมูลใดออกนอกเครือข่ายของโรงพยาบาล
**2. ลักษณะของต้นทุน** API บนคลาวด์คิดค่าบริการตามจำนวนโทเค็นและคำขอไปอย่างไม่มีกำหนด ส่วนโมเดลภายในเครื่องเมื่อดาวน์โหลดแล้ว (ไม่กี่กิกะไบต์ เช่น ประมาณ 2.3 GB สำหรับ bge-m3 รวมกับโมเดลสร้างข้อความ) ไม่มีค่าใช้จ่ายต่อคำแนะนำ เอกสารของคณะผู้จัดทำระบุว่า *"ไม่มีค่าธรรมเนียมต่อรหัส ไม่มีค่าธรรมเนียมต่อผู้ใช้ ... ต้นทุนไม่เพิ่มขึ้นแม้โรงพยาบาลจะให้รหัสมากขึ้น"* (`DEPLOYMENT-PREP.md` ส่วน "What it costs") สำหรับโรงพยาบาลรัฐที่ใช้งบประมาณจาก สปสช. (บทที่ 1 หัวข้อ 1.1) การซื้อ GPU ครั้งเดียวในราคาคงที่ยอมรับได้ง่ายกว่าต้นทุน AI ที่เพิ่มตามจำนวนผู้ป่วยอย่างมาก
**3. ความพร้อมใช้งานและความเป็นอิสระจากผู้ให้บริการ** RAG ออกแบบเป็นบริการ **ทางเลือก** (optional) ส่วนอื่นของระบบยังทำงานได้แม้ปิดบริการนี้ (บทที่ 4 หัวข้อ 4.3) การพึ่ง API บนคลาวด์จะเพิ่มความล้มเหลวจากภายนอก (เครือข่าย ความพร้อมของผู้ให้บริการ) เข้ามาในขั้นตอนที่ต้องการให้ลดระดับการทำงานอย่างนุ่มนวล (degrade gracefully) แทนการล้มเหลวทั้งหมดเมื่อ AI ไม่พร้อมใช้งาน

ข้อแลกเปลี่ยนที่เลือกอย่างชัดแจ้ง คือ **ยอมแลกคุณภาพการค้นคืนและขีดความสามารถของโมเดล เพื่อให้ได้การควบคุมข้อมูลและต้นทุนที่คาดการณ์ได้** โมเดล 0.5B–8B ด้อยกว่าโมเดลระดับแนวหน้า (frontier) บนคลาวด์อย่างเห็นได้ชัด ระบบจึงชดเชยด้วยการยึดโยงกับแหล่งที่มา (การตรวจ `unverified_codes` คำสั่ง "ตอบจากบริบทเท่านั้น" ในพรอมต์ระบบ และชั้นกฎ "แนะนำรหัส (Suggest & Learn)" ที่ผู้ให้รหัสสอน — บทที่ 4) แทนการเพิ่มขนาดโมเดล ซึ่งสอดคล้องกับหัวข้อ 2.2

## 2.4 สิ่งที่งานที่เกี่ยวข้องซึ่งได้ทบทวนไม่ได้ครอบคลุม — ช่องว่างที่โครงการนี้มุ่งเป้า

จากหัวข้อ 2.1–2.3 พบช่องว่าง 3 ประการในงานก่อนหน้าที่โครงการนี้มุ่งเป้า

1. **ไม่พบผลิตภัณฑ์หรืองานวิจัยที่ตีพิมพ์ด้านการให้รหัสโดยมีเครื่องมือช่วยที่รองรับภาษาไทยและ ICD-10-TM** ทุกรายการที่พบมุ่งเป้าระบบรหัสภาษาอังกฤษ ภาษาเยอรมัน หรือภาษารัสเซีย
2. **CAC เชิงพาณิชย์ (หัวข้อ 2.1) เน้นคลาวด์/ระดับองค์กร** ขณะที่โครงการนี้ (บทที่ 3) มุ่งการติดตั้งภายในเครื่อง ทำงานแบบออฟไลน์ได้ และใช้ GPU ไม่เกิน 1 ตัว สำหรับโรงพยาบาลรัฐที่มีทรัพยากรจำกัด แทนระบบสุขภาพเอกชนขนาดใหญ่
3. **งานวิจัย RAG สำหรับการให้รหัสที่ตีพิมพ์แล้ว (หัวข้อ 2.2) วัดผลย้อนหลังเทียบกับเวชระเบียนที่ให้รหัสไว้แล้ว** ไม่มีงานใดนำไปใช้เป็นเครื่องมือสำหรับผู้ให้รหัสแบบมนุษย์ร่วมตัดสินใจ (human-in-the-loop) พร้อมการบันทึกกลับลงระบบสารสนเทศโรงพยาบาลที่ย้อนกลับได้ ซึ่งโครงการนี้สร้างขึ้น (อนุมัติ/เปิดใหม่ บันทึกประวัติเพื่อการตรวจสอบ และการบันทึกกลับตามส่วนต่าง (diff) — บทที่ 4) ส่วนการให้คะแนนรหัสที่ระบบแนะนำเทียบกับการให้รหัสในอดีตของโรงพยาบาลพันธมิตรด้วยวิธีของ Klang et al. (2024) ยังไม่ได้ดำเนินการ เนื่องจากต้องใช้ข้อมูลจริงของโรงพยาบาล (บทที่ 8)
